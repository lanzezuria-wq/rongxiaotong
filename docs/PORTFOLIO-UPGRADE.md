## 后端改动与取舍

| 问题 | 当前实现 | 取舍 |
| --- | --- | --- |
| 改密后其他设备仍能使用旧 Token | 用户 token_version 入库，签发与鉴权匹配版本；改密、禁用和启用时递增 | 沿用原有逐请求查库，不新增 Redis 依赖；所有旧会话同时失效 |
| 并发密码错误覆盖失败次数 | 登录在账号行锁内校验、计数；业务认证失败提交计数 | 同一账号串行，避免把 BCrypt 工作扩散为多账号全局锁 |
| 客户端伪造来源头 | 默认取连接来源，只剥离显式可信代理链 | 代理必须覆盖外来转发头，并配置受信 IP/CIDR |
| 两位管理员同时审核 | UPDATE 携带待审状态且要求影响一行，关联资料同事务处理 | 不以按钮禁用代替服务端状态约束 |
| 普通账号启用绕过专家审核 | 待审核和被拒专家只能走审核流程 | 审批状态与启用动作保持边界 |
| 操作日志表为空 | 关键写操作同步落库；失败管理请求用独立事务记 HTTP 结果；管理员分页检索 | 不保存原始请求正文、密码或 Token；不引入消息队列 |
| 字典删除保护占位 | 查询商品和融资引用，阻止被引用编码删除或变更 | 仍采用应用层引用校验，未引入全库物理外键 |
| 请求内容类型错误变成系统故障 | 显式返回 HTTP 415 和统一业务响应 | 保留既有 JSON 解析与唯一约束分支 |
| 演示配置混入真实部署 | dev/prod 分离、生产配置外置、关闭固定验证码与接口文档 | 未接短信网关时生产注册明确不可用 |

成功审计与业务更新处于同一事务；审计写入失败会使该业务写操作回滚。失败请求的审计写入失败时记录服务端错误，不掩盖原请求结果。审计保留策略和告警属于后续运维工作。

## 原项目报告需要更新的口径

1. 原报告称禁用后旧 Token 仍有效，但原过滤器已查库拦截禁用状态。本次进一步增加凭证版本，防止改密与重新启用后的旧凭证继续使用。
2. 原项目只有 IP 限流保存在内存；账号失败次数与锁定时间已在数据库，不会因重启丢失。
3. 含 DROP TABLE 的初始化脚本是演示重置工具，不能写成“重复执行无副作用”。已有数据库应使用增量迁移。
4. 未引入 Pinia 不代表状态管理错误；本次在现有响应式状态上实现跨标签同步，并以测试验证。
5. 历史 94 用例与当前 105 用例分别对应不同版本；不能把历史截图当作当前通过证据。
6. Mock 风控、审批数值和支付能力均为演示，未接入真实征信、支付或放款。

原始 DOCX 保留为历史材料，本文件给出可直接更新报告的实现事实，避免覆盖原提交版本。
