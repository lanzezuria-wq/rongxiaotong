## 一、项目概述与进度

### 1.1 项目背景

「融销通」是一个面向农户的农产品**融销一体**平台，解决两件事：

- **销**：农户把农产品直接卖给买家（商品发布 → 购物车 → 下单 → 发货 → 收货）；
- **融**：农户获得农业贷款。但农户普遍没有抵押物，所以平台用**联保小组**模式 ——
  3~10 户同行业、同地域的农户组成小组互相担保，银行审的是「小组」而不是个人。

此外还有**专家助力**模块：农业专家发布知识文章、回答农户提问、接受农户预约，
补上"技术指导"这一环。

### ⚠️ 四个必须知道的版本坑

1. **Spring Security 7 的写法与网上教程完全不同。**
   Security 7 移除了 `.and()` 链式写法，只能用 Lambda DSL：
   ```java
   // ❌ 网上 Security 6 教程的写法，在 Security 7 里直接编译不过
   http.csrf().disable().authorizeRequests().antMatchers("/x").permitAll().and()...
   // ✅ 本项目的写法
   http.csrf(AbstractHttpConfigurer::disable)
       .authorizeHttpRequests(auth -> auth.requestMatchers("/x").permitAll())
   ```
   另外 `antMatchers` → `requestMatchers`、`@EnableGlobalMethodSecurity` → `@EnableMethodSecurity`。
   **照抄网上的 Security 6 教程必错。**

2. **springdoc 必须是 3.x。** 文档里写的 2.3.x 只支持 Boot 3；
   在 Boot 4 上引 2.x 的表现是"应用能启动，但 `/swagger-ui.html` 一直 404"，
   很容易误判成路径写错。

3. **MyBatis-Plus 的分页不是自动生效的。** 必须注册 `PaginationInnerInterceptor`，
   否则 `selectPage` 不报错、但**不拼 LIMIT**——把全表查出来塞进 `Page`，
   而且 `total` 还是对的，肉眼看接口完全正常。必须等数据量大到内存扛不住才暴露。
   见 `com.rxt.config.MybatisPlusConfig`。

4. **分页插件依赖 jsqlparser，必须单独引。** 只引 starter 会在运行到分页时报
   `ClassNotFoundException`，因为插件要真正解析 SQL 才能把 LIMIT 插到正确位置。

## 三、架构与包结构

### 3.1 一个关键决策：单模块 + 模块子包

任务包 `07-项目目录结构` 要求拆成 Maven 多模块
（`rxt-common` / `rxt-system` / `rxt-trade` / `rxt-app`），
但 **P1 实际交付的是单模块 `demo1`**。三个人的选择是：

> **继续用单模块，每个模块用自己的子包隔离代码。**

理由（P2 在 `docs/P2-实施方案.md` 里算过这笔账）：

| 方案 | 代价 | 风险 |
|---|---|---|
| 拆成多模块 | 要重构 P1 已推送的 62 个源文件 + 全部 import + 启动类 | **高**。巨量 diff 会覆盖别人的改动 |
| 继续单模块 | 只需改 1 行 `@MapperScan` | 低 |

子包隔离保留了模块边界：真要拆模块时**整包搬走**即可。

### 3.2 包结构

```
com.rxt
├── common/                     ← P1：统一响应、错误码、常量、异常、工具
│   ├── Result / ResultCode / PageResult
│   ├── constant/               UserConst / DictConst / ArticleConst / AuditConst
│   ├── exception/              BizException / ResourceNotFoundException / GlobalExceptionHandler
│   └── util/                   DateUtils
├── config/                     ← P1：Security / MyBatis-Plus / OpenAPI / Password
├── security/                   ← P1：JWT 过滤器、LoginUser、SecurityUtils、限流器
├── entity/ mapper/ dto/ vo/    ← P1：User / Expert / DictItem / Article
├── service/ controller/        ← P1：用户体系 M1 + 系统管理 M7
│
├── trade/                      ← P2：M2 首页 + M3 农产品交易
│   ├── constant/               ProductConst / OrderConst
│   ├── entity/ mapper/ dto/ vo/
│   ├── service/ service/impl/
│   ├── controller/             ProductController / CartController / OrderController
│   │                           AddressController / HomeController
│   └── util/                   TradeJsonUtil
│
├── finance/                    ← P3：M4 融资服务 + M6 融资管理
│   ├── config/                 MockConfig（Mock 开关与生成器）
│   ├── constant/               FinancingConst（两条状态机 + 阈值）
│   ├── entity/                 FinancingApply / GuaranteeGroup / GuaranteeMember / BankApproval
│   ├── mapper/ dto/ vo/
│   ├── service/ service/impl/  FinancingService / BankService
│   └── controller/             FinancingController / BankController
│
└── assist/                     ← P3：M5 专家助力
    ├── constant/               AppointmentConst
    ├── entity/                 ArticleComment / ArticleLike / Question / Appointment
    ├── mapper/ dto/ vo/
    ├── service/ service/impl/  ArticleService / ExpertService / ConsultService
    └── controller/             ExpertController / QuestionController / AppointmentController
```

**P3 为什么分成 `finance` 和 `assist` 两个包，而不是合成一个（像 P2 只用一个 `trade`）？**

因为 P3 管的三个模块分属两个业务域：
M4（融资申请）与 M6（银行审批）共享同一条状态机和同一张 `t_guarantee_group`，
耦合很紧，必须在一个包；而 M5（文章/专家/提问/预约）是完全独立的领域。
合成一个包会让"哪些类属于融资、哪些属于专家"只能靠文件名猜；
分成两个包则一眼可辨，将来拆模块也是两条清晰的边界。

### 3.3 分层约定（三人统一）

```
Controller  →  Service（接口）  →  ServiceImpl  →  Mapper（继承 BaseMapper，无 XML）  →  Entity
                     ↑                                  ↓
                    DTO（入参）                       VO（出参）
```

四条铁律：

1. **Controller 必须很薄** —— 只做三件事：`@Valid` 触发参数校验、
   用 `SecurityUtils` 取当前用户、把返回值包成 `Result`。
   如果在 Controller 里写 `if` 判断业务规则，说明代码放错层了。
2. **Service 全程抛 `BizException`，绝不 `return Result`** ——
   否则事务回滚会失效（抛异常才回滚，return 不会），
   而且业务数据要从 `result.getData()` 里往外掏。
3. **不过滤敏感字段靠 VO** —— 所有出参都过 VO 转换，
   从结构上保证密码之类的东西不会被返回（`PageResult.of(page, UserVO::from)` 就是这道闸门）。
4. **VO 里日期一律用 `String`** —— 见第八节的说明。

## 四、数据库设计

### 4.1 ⚠️ 建表脚本必须按顺序执行

数据库 `rxt_db`，三个脚本**顺序不能反**（后面的依赖前面的表和种子账号）：

```bash
mysql -uroot -p < demo1/src/main/resources/sql/init.sql
mysql -uroot -p < demo1/src/main/resources/sql/init_trade.sql
mysql -uroot -p < demo1/src/main/resources/sql/init_p3.sql
```

| 脚本 | 归属 | 内容 | 幂等 |
|---|---|---|---|
| `init.sql` | P1 | 建库 + 5 张表 + 7 个种子账号 + 22 条字典 + 4 篇示例文章 | ✅ 先 DROP 再建 |
| `init_trade.sql` | P2 | 6 张表 + 1 个买家账号 + 8 个商品 + 2 个订单 | ✅ 先 DROP 再建，用户用 `INSERT IGNORE` |
| `init_p3.sql` | P3 | 8 张表 + 给 2 张 P1 表补 4 列 + 6 个账号 + 演示数据 | ✅ 先 DROP 再建，补列用存储过程判断存在性 |

**为什么每个模块一个脚本，而不是都并进 `init.sql`？**
因为那样同一份 DDL 会存在两处。四个人并行开发时，谁改了列却只改一处，
两边就会静默不一致 —— 这类问题极难排查。各自维护增量脚本，职责边界清楚。
P1、P2、P3 三个人**独立地做出了同一个选择**，说明这个约定是成立的。

### 4.3 冗余计数字段：一处刻意的设计

数据库里有 6 个"能算出来但仍然存一份"的计数字段：

| 字段 | 可从哪算出来 | 谁负责刷新 |
|---|---|---|
| `t_guarantee_group.total_amount` | `SUM(t_guarantee_member.apply_amount)` | `FinancingServiceImpl#syncGroupState` |
| `t_guarantee_group.current_members` | `COUNT(t_guarantee_member)` | 同上 |
| `t_article.view_count` / `like_count` / `comment_count` | `COUNT(t_article_like)` 等 | `ArticleServiceImpl` |
| `t_expert.answer_count` | `COUNT(t_question WHERE answer_by=?)` | `ConsultServiceImpl#answer` |

**为什么冗余？** 因为列表页要展示这些数字。如果不冗余，一页 10 条就是 10~20 次
额外 count 查询。冗余的代价是"必须同步更新"，所以规则是：

- **每个冗余字段只有一个刷新入口**（上表右列），别处一律不许直接改；
- **聚合类的（小组人数/总额）用"重新 SUM/COUNT"而不是 ±1** ——
  ±1 看起来省一次查询，但只要有一次漏改（异常、新加的分支忘了调），
  数字就永久错，而且**没有任何信号**。重算则是幂等的，调 10 次结果一样；
- **计数类的（点赞/评论/回答数）用 SQL 表达式自增**（`setSql("like_count = like_count + 1")`），
  让数据库在行锁下自己算，避免并发丢计数；减法一律套 `GREATEST(0, x - 1)` 保下界。

### 5.3 P2 · M2 首页 + M3 农产品交易（25 个）

**订单状态机**（P2 的核心，与 P3 的融资状态机是同一套思路）：

```
0 待付款 ──支付──> 1 待发货 ──发货──> 2 已发货 ──收货──> 3 已完成
   │
   └──取消／15 分钟超时──> 4 已取消
```

必须守住的：状态只能按箭头走、扣库存要加行锁（`SELECT ... FOR UPDATE`）、
创建订单是一个事务、取消订单要还库存、越权校验必须在 Service 比对 `farmer_id`/`buyer_id`
（只靠 `hasRole` 不够）。

## 六、P3 核心业务设计

### 6.1 两条状态机（P3 的全部复杂度都在这里）

**融资申请 `t_financing_apply.status`**

```
0 待匹配 ──加入小组──> 1 已匹配 ──小组满 3 人成型──> 2 待银行审批
                                                        │
                                       银行通过 ──> 3 已通过
                                       银行拒绝 ──> 4 已拒绝

任意进行中(0/1/2) 且小组未被银行处理 ──申请人取消──> 5 已取消
```

**联保小组 `t_guarantee_group.status`**

```
0 招募中（<3 人） ──人数达 3──> 1 已匹配（成型，进入银行待审池）
    ↑                                        │
    └──有人退出，人数<3，自动退回──────────────┘
                                            3 已通过 / 4 已拒绝（不可撤回）
```

**三点必须理解的地方：**

1. **小组成状态机里的 `2 待银行审批` 是预留位。**
   本项目是"成型即入池"，不需要农户或平台再点一次"提交银行"，
   所以正常流程不会停在 2。保留它是为了兼容文档定义，以及将来要加
   "线下材料齐了再提交"的流程时不用改表结构和前端字典。
   银行端筛"待审批"时同时认 1 和 2，就是为了兼容这两种语义
   （`FinancingConst.GROUP_PENDING_STATUSES`）。

2. **银行审的是「小组」不是个人。**
   一次审批把小组和组内**所有**申请一起改状态。
   `t_bank_approval` 挂在 `group_id` 上而不是 `apply_id` 上。
   三处状态（审批记录、小组、组内申请）必须同时变，所以 `approve` 整个方法在一个事务里。

3. **成型/退回的联动只有一处入口：`FinancingServiceImpl#syncGroupState`。**
   任何成员变动（加入小组、退出/取消申请）之后都调它，它做三件事：
   重算冗余列（重新 SUM/COUNT，不做 ±1）→ 按"人数是否 ≥3"双向修正小组状态
   → 联动推进/回退组内申请状态（1 ↔ 2）。
   **别处不允许直接改 `current_members` / `total_amount` / `status`。**
   把"进"和"退"放在同一个方法里，行为天然对称，
   不会出现"join 里判断了成型、cancel 里忘了判断退回"这种分叉。

### 6.2 几个刻意的业务约束

| 约束 | 在哪校验 | 为什么 |
|---|---|---|
| 同一用户同时只能有**一条进行中**申请 | `assertNoActiveApply` | 否则"加入小组用哪条申请""审批通过按哪条放款"到处产生歧义 |
| 发起小组**必须已有一条待匹配申请** | `createGroup` | 小组在业务上就是"一组融资申请的集合"；允许创建空小组会产生"1 人小组没人加入"的垃圾数据，而且发起人自己也进不去 |
| 可加入的小组**只含"招募中"的** | `matchGroups` | 往一个材料已提交银行的小组里加人，会让银行已核定的额度依据失效（银行审的是"这 3 个人"的联保结构） |
| 匹配是**同行业 + 同省强匹配** | `matchGroups` | 联保的核心是"同一区域、同一产业，风险同源、便于互相监督" |
| 取消申请会**物理删除**成员记录 | `cancel` | `join_status=2` 的语义是"被拒绝加入"，与"自己主动退出"不同；而且唯一索引会让旧记录挡住"重新加入同一小组" |
| 审批结果**不可撤回** | `approve` 两层判断 | 小组状态是否终态 + 审批表里是否已有该 group 的记录。后者是数据兜底：万一组状态因 bug 没改成功，有审批记录仍能挡住第二次审批 |
| 拒绝审批**必须填理由** | `approve` | 跨字段条件必填，Bean Validation 表达不了；理由要留给农户看，否则他只知道被拒、不知道该改什么 |

### 6.3 按角色分视角的两个接口（联调重点）

契约里 `GET /api/question/list` 和 `GET /api/appointment/list` 的说明都写的是「我的」，
但**同一份数据对两种角色意义不同**：

| 角色 | 提问列表看到 | 预约列表看到 |
|---|---|---|
| 普通用户（farmer） | 我提的问题 | 我发起的预约 |
| 专家（expert） | 别人点名问我的 + 面向所有专家的公开提问 + 我自己提的 | 约给我的 + 我发起的 |

**为什么要这样？** 契约里没有单独的"专家待办列表"接口。
如果两个角色看到同一份数据，专家就永远找不到自己该处理的请求。
所以只能让同一个接口按角色返回不同数据。

> ⚠️ **这一处必须在联调时和 P4 明确**，否则前端会把专家页的数据源接错。
> 另外注意：`role=expert` 但资质**还没审核通过**的用户（`t_expert` 里没有行）
> 看不到待办，只能看到自己作为普通用户提的问题/发起的预约 —— 这是刻意的，
> 他本来也答不了。

### 6.4 Mock 模式（银行审批）

配置：

```yaml
rxt:
  mock:
    enabled: true        # 总闸（P3 新增）
    verify-code: "111111" # P1 的注册验证码
```

| 开关 | 审批接口的行为 |
|---|---|
| `enabled: true` | **只传 `groupId + result` 就能走完流程**：信用分 60~100、利率 3.85~7.00、核定额度按申请总额的 80%~100% 由 `MockConfig` 自动生成 |
| `enabled: false` | 这三项必须由前端传全，否则报 1001。**故意不自动生成** —— 真实审批里让系统自己编利率是不可接受的 |

生成规则上有两个细节值得记：
- 利率与额度用"整数分/整数百分比"生成再除，**从生成那一刻就没有精度问题**
  （`nextDouble()` 会产出 `5.4783219…` 这种无限小数，而利率业务上是精确到分的）；
- `setScale(2)` 必须显式给 `RoundingMode.HALF_UP`，否则会抛 `ArithmeticException`。

## 七、安全与权限模型

### 7.1 角色

| 角色 | 说明 | 怎么来 |
|---|---|---|
| `farmer` | 农户（**与买家共用此角色**） | 自助注册，注册后即正常 |
| `expert` | 农业专家 | 自助注册，需管理员审核（`t_user.status=0 → 1`，并写入 `t_expert`） |
| `bank` | 银行人员 | **不能自助注册**，由管理员创建 |
| `admin` | 平台管理员 | 同上 |

`UserConst.REGISTER_ROLES = {farmer, expert}` 是注册接口的白名单 ——
不校验的话，任何人都能 POST 一个 `"role":"admin"` 把自己变成管理员。

### 7.2 权限配置总表（`SecurityConfig`，按顺序匹配）

```
permitAll    : /api/ping
             : /api/user/register, /api/user/login
             : /swagger-ui/**, /v3/api-docs/**, /error
             : GET  /api/article/**        ← 游客可读文章列表/详情
             : GET  /api/expert/**         ← 游客可读专家列表/详情
             : GET  /api/home/**           ← 游客可读首页
             : GET  /api/product/**        ← 游客可读商品
authenticated: GET  /api/admin/dict/**    ← 必须在下面那条之前，因为下拉框所有人都要用
hasRole admin: /api/admin/**
             : PUT  /api/article/{id}/audit   ← 不在 /api/admin/** 下，必须单独配
hasRole bank : /api/bank/**
hasRole farmer: POST/PUT/DELETE /api/product/**
authenticated: 其余一切（含 /api/financing/**、/api/question/**、/api/appointment/**、
              /api/cart/**、/api/order/**、/api/address/**）
```

### 7.3 三层权限冗余（挡的不是同一件事）

以银行审批为例，说明为什么三层都要有：

1. `SecurityConfig` 的 `/api/bank/** → hasRole("bank")` ——
   **请求进不来**（最早、最省资源的拦截）；
2. `BankController` 上的 `@PreAuthorize("hasRole('bank')")` ——
   **方法级兜底**。万一将来有人为了放行某个新接口把 `/api/bank/**` 改成
   `authenticated()`，注解仍然拦得住。这是"防御性冗余"而不是重复劳动；
3. `BankServiceImpl#requireBankUser` 查库 ——
   挡住"**Token 里的角色是签发时的快照**、而现在角色已经被管理员改掉"这种过期权限。

### 7.4 为什么"角色要求"不全写在 URL 规则里？

P3 的融资、提问、预约接口的角色要求是**"按动作"而不是"按路径"**的：

- 融资申请 / 发起小组 → 只有农户（Service 校验）；
- 融资申请详情 → 本人，但 admin / bank 也要看（审批需要）；
- 加入小组用的申请归属 → 必须是自己的申请（Service 校验）；
- 专家回答 / 处理预约 → 必须是**记录归属的那个专家**。
  这一条 URL 规则**根本表达不了**：它要判断"你的 `t_expert.id`
  是不是这条记录的 `expertId`"，而两个人的 `role` 都是 `expert`。

硬要写成多条互相穿插的 URL 规则，只会既难读又容易漏。
所以统一收在 Service 里用普通 `if` 表达，读起来更清楚。

### 7.5 越权防护的另一半：接口形状

所有接口都**不接收 `userId` 参数**，身份一律从 Token 取
（`SecurityUtils.currentUserId()`）。
这样"用别人的 id 查别人的数据"这类攻击面**从接口形状上就不存在**，
不需要靠额外校验去堵。

## 八、统一约定（前后端契约）

### 8.1 响应体

```json
{ "code": 0, "message": "操作成功", "data": { } }
```

**关键：HTTP 状态码和业务错误码是两套东西。**
`code=1002`（密码错误）时 HTTP 也是 401；`code=1001`（参数校验失败）时 HTTP 是 400。
**前端判断成功只看 `code === 0`**，不要看 HTTP 状态码 ——
因为网络层异常（502、超时）也会是非 200，两者要分开处理。

P1 的 `frontend/src/api/request.js` 已经把这件事处理好了：拦截器两处都读，
非 2xx 时按 business code 分流（1002/1006 跳登录页、1007 只提示不跳、
1005 限流提示、其余统一报错）。

### 8.2 错误码分段

| 段 | 归属 | 已定义 |
|---|---|---|
| 1xxx | 通用 / 用户 | 1000 系统 1001 参数 1002 登录失败 1003 禁用 1004 验证码 1005 限流 1006 Token 过期 1007 无权限 **1008 资源不存在**（补充码） |
| 2xxx | 交易 | 2001 库存不足 **2002 订单状态不允许**（P2 补） 2003 已下架 2004 购物车空 |
| 3xxx | 融资 | 3001 已有进行中申请 3002 小组满员 3003 已被银行处理 **3004 仅农户 3005 小组不可加入 3006 已审批 3007 申请已被占用**（P3 补） |
| 4xxx | 专家助力 | **4001~4006**（P3 新增，见第九节） |

### 8.3 分页

```json
{ "records": [...], "total": 42, "page": 1, "size": 10, "pages": 5 }
```

⚠️ 契约里写的是 `{total, list}`，而 P1 实现的是 `{records, total, page, size, pages}`。
**以实现的为准**（P2 也已跟随）。前端只需认 `records` 和 `total`。

### 8.4 时间与金额

- **时间**：一律 `yyyy-MM-dd HH:mm:ss`，`Asia/Shanghai`。
  **VO 里不暴露 `LocalDateTime`，只暴露格式化好的 `String`**（`DateUtils.format`）。
  原因：Boot 4 的 Web 层换成了 Jackson 3（`tools.jackson`），而 Jackson 2 还在类路径上
  （jjwt 传递引入）。`LocalDateTime` 默认序列化成 `2026-09-18T14:05:17`（带 T），
  而需求要的是空格分隔。想统一格式通常靠 `@JsonFormat` 或全局配置，
  但这两者都和 Jackson 主版本强耦合，换版本行为就变。
  把格式化提前到 VO 转换这一步，输出格式就 100% 可控。
- **入参时间**用 `String` 接收（如预约的 `appointmentTime`），由 `DateUtils.parse` 解析。
  它兼容 `"yyyy-MM-dd HH:mm:ss"` 和 ISO 带 T 格式，解析失败返回可读提示而不是
  Jackson 的英文异常。
- **金额**一律 `BigDecimal`，绝不用 `double`；
  也绝不用 `new BigDecimal(0.1)`（那会得到 `0.1000000000000000055…`）。
- **金额单位**：元，保留 2 位小数。

1. **分类/用途/行业/期限最终统一到哪一套？**（字典编码 还是 契约枚举）
   现在取并集是"两边都能跑"的临时方案，但它意味着**前端下拉框可能有重复选项**
   （`SEED` 和 `material` 都合法），长期看要收敛成一套。
2. **`t_article` 要不要新增 `article_category` 字典类型？**
   现在文章分类借用了 `product_category` 的值，语义上不精确。
3. **依赖种子数据条数的断言要不要保留？**
   见 11.3 —— P1 的 `m7UserList` 曾因别人加种子账号连续红过两次，本次已改成不变量断言。

### 10.6 ⚠️ 本机环境的三个坑（换机器可忽略）

1. **`JAVA_HOME` 被设成了 `F:\New Folder`（一个 node 目录），直接跑 `mvn` 会报
   `找不到或无法加载主类 org.codehaus.plexus.classworlds.launcher.Launcher`。**
   需要显式指定 JDK 17 与 Maven，并且**必须用 Windows 风格路径**
   （`F:/...`，MSYS 的 `/f/...` 形式 java.exe 不认）：
   ```bash
   "F:/jdk-17.0.9/bin/java" \
     -classpath "F:/apache-maven-3.9.16-bin/apache-maven-3.9.16/boot/plexus-classworlds-2.11.0.jar" \
     -Dclassworlds.conf=".../bin/m2.conf" -Dmaven.home="..." \
     org.codehaus.plexus.classworlds.launcher.Launcher <goal>
   ```
2. **surefire 跨盘会崩**（项目在 E:、JDK 在 F:），报
   `forked VM terminated without properly saying goodbye` /
   `'other' has different root`。解法：`mvn test -DforkCount=0`。
   ⚠️ `forkCount=0` 时 `-DargLine=...` **完全失效**（没有 fork 就没有 argLine），
   要把配置作为 **Maven 系统属性**传：`-Dspring.datasource.url=...`。
3. **本机 MySQL 的 root 密码不是配置里的那个。**
   验证时用 `mysqld --no-defaults --initialize-insecure --datadir=<临时目录> --port=3307`
   起了一个**独立实例**（root 空密码），完全不碰用户的 3306 数据。
   这个方法值得保留：**不改用户环境就能做真实验证。**

### 11.3 一处需要说明的测试改动

P1 的 `ApiIntegrationTest.m7UserList` 原本断言"用户总数 = 7"，而这个数字：

- 被 **P2 打破过一次**（他加了演示买家 `13900000008`，变 8，提交时没同步 → 提交后测试是红的）；
- 会被 **P3 再打破一次**（P3 加 6 个账号 → 变 14）。

**所以 P3 把它改成了不依赖种子数量的断言**，校验真正的不变量：

| 原断言 | 现断言 |
|---|---|
| `total == 7` | `total >= 7`（下界）+ 分页结构自洽 |
| `role=expert` 的 `total == 3` | 返回的**每一条**都是 `role=expert`（筛选功能的不变量） |
| `role=expert&status=0` 的 `total == 2` | 待审专家列表**包含** `13900000003`（审核页真正依赖的锚点） |
| `pages == 3` | `pages == ceil(total / 3)`（用返回值现算） |
| `keyword=李农户` 的 `total == 1` | 保持不变（本来就与总量无关） |

> 原来的断言本质上是在"数 SQL 脚本里的行数"，并没有校验业务规则，
> 却让每次有人加种子数据都要回来改数字，漏改的代价是整条流水线变红。
> 改成不变量断言后，**以后谁加种子账号都不会再弄红它。**

## 十二、已知问题与后续计划

### 12.1 已知问题

| # | 问题 | 影响 | 建议 |
|---|---|---|---|
| 1 | 分类/用途/行业/期限存在**两套取值口径**（字典编码 vs 契约枚举） | 前端下拉框可能有重复选项 | 组内定稿收敛成一套（见 9.4） |
| 2 | `GET /api/financing/{id}` 的响应里**嵌了 `group` 对象，而 `group` 也有 `status` 字段** | 前端取值容易拿错（响应字段是字母序输出的，`group` 排在 `status` 前） | 已在前端注释与本文档标注；长期可考虑把 `group.status` 改名或下沉为 `groupStatus` |
| 3 | `t_article.tags` 在 P1 的 `ArticleVO` 里是 `String`（逗号分隔），在 P3 的 `ArticleDetailVO` 里是 `String[]` | 同一个字段两种形状 | 契约如此；已在两个 VO 的注释里说明 |
| 4 | 浏览量 `view_count` 只做简单 +1，**没有去重** | 刷新一次涨一次 | 精确统计要上 Redis 或日志分析，超出本模块范围 |
| 5 | 文章详情接口**没有分页评论**（固定取最近 50 条） | 热门文章看不到更早的评论 | 契约没定义评论分页；真需要时加 `GET /article/{id}/comments?page=` |
| 6 | 订单 15 分钟超时**没有定时任务**，靠"查列表时顺手置超时" | 长时间没人查列表就不会被取消 | P2 在方案里说明过；演示够用 |
| 7 | `t_product_demand`（求购需求）**建了表但没实现接口** | 空表 | 任务包标了"可延后"，P2 也标了可延后 |
| 8 | 小组成员状态 `join_status` 的 0/2 是预留值 | 无实际使用 | 本项目小组是农户自治、无组长审批动作；保留是为了将来加"申请制"时不用改表 |

### 12.2 后续计划

**P4 前端联调时的重点**（P3 视角）：

1. **专家页的数据源**：`/question/list` 和 `/appointment/list` 是按角色分视角的，
   专家登录时返回的是"待办"而不是"我提的"（见 6.3）；
2. **`id` 语义**：专家相关接口传的是 `t_expert.id`，
   而管理员的专家审核接口传的是 `t_user.id`（见 9.3 第 10 条）；
3. **点赞不要自己 ±1**：直接用返回值里的 `isLiked` / `likeCount` 覆盖本地值；
4. **响应字段是字母序**：取值时按字段名取，不要按位置；
5. **分类下拉框**：可以同时展示"字典里的分类"和"契约枚举"，
   但要知道后端两套都收（见 9.4）。

**若要继续开发，建议的顺序**：
补 `t_product_demand` 接口 → 评论分页 → 浏览量去重 → 通知（提问被回答/预约被处理时推送给用户）
→ 联保小组的"申请加入需组长确认"流程（把 `join_status` 的 0/2 用起来）。
